## 1. 产品定位与硬约束

| 项 | 内容 |
| --- | --- |
| 定位 | **单人自用**的 Android 通知过滤工具，侧载安装，不上架应用商店 |
| 目标设备 | 小米 15 / 澎湃 OS3（Android 15）为主，`minSdk 26` 兼顾旧机 |
| 联网 | **默认完全离线**。唯一联网场景 = 用户主动配置的 WebDAV 备份 |
| 账号 / 遥测 | 无账号、无埋点、无崩溃上报、无广告 SDK |
| 包名 | `com.local.notificationfilter` |
| 界面语言 | 简体中文 |
| 数据 | 全部落本机（Room + DataStore），卸载即清空 |

三条不可妥协的产品红线（后续迭代都不能破）：

1. **不引入账号体系与云同步**。备份是「用户自己的文件夹 / 用户自己的网盘」，不是我们托管。
2. **不为了功能加不必要的权限**。当前权限清单见 §6，新增任何权限都要有功能必要性论证。
3. **规则是「先命中先处理」**，不做「多规则叠加执行」。语义简单可预测，优先于功能丰富。

## 2. 功能需求

### 2.1 通知监听与流水

- 基于 `NotificationListenerService` 接收全量通知；进程被杀后由系统重连（`onListenerConnected` 重新绑定管线）。
- 每条通知进入 `NotificationPipeline`（**单线程 scope**，保证同 key 顺序性），依次做：
  黑名单判定 → 规则匹配 → 动作执行 → 落流水 / 统计。
- **快照**：把 `StatusBarNotification` 归一成 `NotificationSnapshot`（key / notifId / 包名 /
  应用名 / title / text / textLines / subText / summaryText / people / extras 全量 / postTime /
  isOngoing / media 字段）。
- **流水合并（关键行为）**：同一条**存活**通知在流水里只占一行。
  判定：`0 ≤ now - lastWriteAt ≤ 10 分钟` → 就地改写该行（不动 `recordId`，列表不跳顶）；
  `onNotificationRemoved` 是权威失效信号，同 key 再来才另起一行。
  合并时统计只计一次（`alreadyCounted = true`），避免下载 / 音乐类通知把统计刷爆。
- 流水表滚动淘汰：保留最近约 1000 条。
- 总开关暂停期间：仍记录流水，但不跑规则；合并行必须把结果重置为「放行」，
  不能保留暂停前的结论（否则用户会看到「放行」的通知挂着「消除」标签）。

**验收**：同一条下载通知每秒刷新 10 次，流水里始终只有一行，内容跟着变，位置不动。

### 2.2 规则引擎

一条规则 = **匹配条件 + 作用范围 + 动作 +（可选）设备状态条件**。

- **匹配模式**（8 种，规则级单选）：
  `ALL_CONTENT`（全部内容）/ `TEXT_ANY`（包含任一）/ `TEXT_ALL`（包含全部）/
  `TEXT_NOT_ANY`（不包含任一）/ `TEXT_NOT_ALL`（不包含全部）/ `TEXT_A_NOT_B`（包含 A 且不含 B）/
  `REGEX`（正则，可指定 `ignoreCase` 与目标字段）/
  `TEXT_GROUPS`（V12.2 分组匹配：关键词分多组，**组间 AND**——每组都要满足；组内可选
  「任一出现」/「全部出现」。每个关键词仍在任一被选字段中查找，可分别出现在不同字段）。
- **匹配字段**：文本类 6 项（TITLE / TEXT / TEXT_LINES / SUB_TEXT / SUMMARY_TEXT / PEOPLE）
  + 元信息类（key / id / tag / channelId / pkg / time 等）+ **任意 extras 字段**（大小写敏感）
  + `media.*` 媒体字段（来自活跃 MediaSession，按需采集）。
- **作用范围**：全局 / 仅指定 App / 全局但排除指定 App。
- **优先级**：按 `order` 升序，**先命中先执行**，一条通知只执行最靠前的那条规则的动作为止。
  黑名单优先于一切规则。
- **设备状态条件**：屏幕亮/灭、充电中/未充电、时段（起止分钟 + 生效星期），全空 = 无限制。
- **正则编译缓存**：按 `(pattern, ignoreCase)` LRU 缓存（容量 128）。
  规则匹配与内容提取各有独立缓存——**正则在热路径上绝不能重复编译**。
- **规则内存缓存**：`RuleRepository.getAll()` 带进程内缓存，任何写操作后必须失效。

**验收**：规则编辑页的「测试」只统计当前这一条规则，且用**未保存的草稿**跑；
面板必须显式展示「本次按关键词：xxx」，否则用户无法判断草稿是否生效。

### 2.3 六种动作

| 动作 | 语义 | 备注 |
| --- | --- | --- |
| 消除 `BLOCK` | 从通知栏撤掉 | 子选项「静音消除」= 先把该渠道静音再撤（作用到该渠道后续通知，用户已确认接受） |
| 推迟 `SNOOZE` | 撤掉后到点重新发回 | 可设多个时刻；用 `AlarmManager.setExactAndAllowWhileIdle`；重启后重排 |
| 替换 `REPLACE` | 用自定义标题/正文重发 | 复用原 `contentIntent`；可保留图标 / 大图 / 渠道名；与推迟组合走 App 自建延时重发（`pending_reposts` 表） |
| 朗读 `READ_ALOUD` | TTS 读出来 | 惰性绑定引擎，空闲 5 分钟释放；不可用时记 `READ_ALOUD_SKIPPED` |
| 弹幕 `DANMAKU` | 屏幕飘一条，**不撤原通知** | 需悬浮窗权限 |
| 悬浮 `FLOAT` | 指定位置显示卡片，**不撤原通知** | 需悬浮窗权限；支持条件显示与常驻 |

- 一条规则可配多个动作。执行顺序：朗读 → 消除 / 推迟 / 替换 → 屏幕显示类。
- 动作执行留痕：`ActionType` 共 9 个（含 3 个失败留痕 `READ_ALOUD_SKIPPED` /
  `REPLACE_FAILED` / `OVERLAY_SKIPPED`），流水里**失败标签用错误色**，不能显示成「放行」。
- 「效果」是多值的：`NotificationRecord.effectKinds` 由 `executedActions` 派生
  （`ActionType.resultKind()` 去重保序），列表最多显示 2 个 + `+N`，详情页显示更多；
  筛选按「任一效果命中」匹配。

### 2.4 覆盖层（弹幕 / 悬浮）

- `WindowManager` + `TYPE_APPLICATION_OVERLAY`，每条弹幕/每个悬浮各一个全宽窗口，
  内部 `ComposeView`；窗口设 `FLAG_NOT_TOUCHABLE`（点击穿透）。
- **弹幕两种形态**：贯穿式（右→左滚动，`occupiedTracks` 做最小未占用轨道分配）/
  定位式（九宫格 + 偏移，多条按实测高度堆叠）。
- **样式**：颜色 / 渐变（线性、径向）/ 圆角 / 四边内边距 / 字号 / 字重 / 透明度 /
  边缘羽化 / 出现与消失动画（各自独立、各设时长）。
- **零动画**必须是真·零动画（直接 `snapTo(1f)`），不能「倒放入场进度」。
- **悬浮**支持常驻（停留 0 秒）与条件显示（某 App 有通知 / 屏幕亮灭 / 充电 / 时段 / 前台 App）。
- **悬浮多窗口**（V12）：不同规则的悬浮窗按规则 id **一规则一窗**同时显示、互不顶掉；
  同停靠位 + 同偏移的多个窗口按显示顺序级联避让（步进 14dp），同屏上限 8 个（安全阀，
  达上限撤最早的）。悬浮显示条件的「目标规则」（V12.1 起**可多选**）：每条条件可指定
  显示 / 清除同时作用于**哪些规则**的悬浮窗（各用它们自己的样式与内容；留空 = 本条规则
  自己的）；V12.0 的单选值经 `allTargetRuleIds` 自动并入，老数据行为不变。
- **媒体字段实时驱动**（V12.1）：`media.*` 变化时（播放 / 暂停 / 切歌，播放器不重发通知），
  对**通知栏全量存活通知**重跑「引用了 `media.*` 的启用规则」——匹配 → 动作 → 命中事件
  （`emitMatched`）全链路走通，于是引用媒体字段的规则能实时驱动悬浮显示条件
  （典型：`media.playing = false` → 撤掉某条规则的悬浮窗）。已有 `liveRecords` 行的通知
  同时就地刷新流水内容；没有行的存量通知只求值、不落库（不插新行、不改历史、不重复计数）。
- 进程被系统回收时窗口静默消失——已接受，不做守护进程。

### 2.5 内容提取与聚合

- 提取器 `ExtractorConfig`：列表号 1..9、字段集合、字段分隔符、正则、忽略大小写、
  捕获格式（`$0` 整段 / `$1`..`$9` 捕获组）、去重、条数上限、启用开关。
- 两组占位符：
  - `{re1}~{re9}`：**只从当前这一条通知**即时提取（不读库）；
  - `{items1}~{items9}`：跨通知**累积**（写 `aggregation_items` 表，按时间汰旧）。
- 输入长度上限 8KB、单次最多 200 个匹配（防 ReDoS 放大，属缓解不是根治）。
- 非法正则 → 返回空列表，**绝不抛异常**（引擎正跑在真实通知上）。

**验收**：启用 + 正则非空 + 上限 > 0，三者缺一，`{reN}` 必须被判为「未识别占位符」
并在 UI 上提示；编辑页要能「用通知栏第一条通知试提取」当场验证。

### 2.6 黑名单

- 按包名列表，命中即无条件消除，优先于一切规则。
- 与应用列表选择器共用 `AppUtils.installedApps()`（**枚举全部已安装应用**，
  不按「有桌面图标」过滤；该权限见 §6 `QUERY_ALL_PACKAGES`）。

### 2.7 统计与搜索

- 统计按「包名 × 天」聚合在 `stats_daily` 表（不做全表扫描）：
  过滤数 / 放行数；「屏幕显示」类动作**不计入过滤**。
- 首页三张卡可点击跳转到记录页并预置过滤条件（消除 / 放行 / 在跑规则）。
- 全量搜索：按关键词 + 字段 + 结果 + 时间范围，SQL `LIKE` 预筛 + 内存精筛，候选上限 2000。

### 2.8 备份与恢复

- **备份内容**：规则 + 黑名单 + 5 项应用设置（总开关 / 主题 / 深浅 / 常驻通知 / 多任务隐藏）。
  权限引导状态、流水、统计**不备份**（设备相关或体量过大）。
- **两个目标**：本地文件夹（SAF `ACTION_OPEN_DOCUMENT_TREE` + `takePersistableUriPermission`）
  与 WebDAV（面向坚果云，但只用标准动词，Nextcloud / 群晖同样可用）。
- **文件命名**（`BackupNames`，纯函数、可单测）：
  - 手动 `nf-backup-yyyyMMdd-HHmmss.json` —— 永不自动删除；
  - 自动 `nf-auto-yyyyMMdd-HHmmss.json` —— 保留最近 30 份，更早的自动删；
  - 恢复前快照 `nf-before-restore-yyyyMMdd-HHmmss.json` —— 保留最近 5 份。
  - 时间戳定宽补零 ⇒ **字典序 = 时间序**，清理只按前缀分类，绝不误删手动备份。
- **自动备份**：`AlarmManager.setAndAllowWhileIdle`（不用 exact，避免权限与每日次数限制）
  + 一次性闹钟自续期；重启后由 `BootReceiver` 重排。
- **恢复**：两步式（先读文件出预览 → 用户确认才写库）。
  规则**永远追加**（不删现有规则），黑名单与设置按「全部恢复」覆盖；
  恢复前自动写快照，写失败不阻断恢复但在报告里注明。
- **WebDAV 传输层必须是自研 `RawHttp`**（原生 Socket 手写 HTTP/1.1），
  见 §5 红线第 1 条。
- 本地与云端备份文件**都支持删除**，删除需二次确认。

### 2.9 设置与主题

- 总开关、常驻状态通知（默认关）、多任务中隐藏、深浅模式、六个主题（含主色派生）。
- 主题的 `secondary` / `tertiary` 系一律**从主色派生**，保证 chip / 分段按钮 / 统计页自动跟随。
- 动作语义色独立于主题（`ActionColors`），避免「消除」与「放行」撞色。

### 2.10 权限引导与内置帮助

- 权限引导页逐项检测 + 一键跳转（通知使用权 / 悬浮窗 / 无障碍（按需出现）/
  电池优化 / 后台弹窗 / 自启动）。
- App 内「使用说明」页（9 节，默认折叠）——**功能的使用方法必须写进 App**，
  不能只写在 Markdown 里（用户在手机上配规则，翻文档的摩擦等于没有说明）。

## 3. 数据模型

### 3.1 规则（Room 单列 JSON）

```text
rules(id, name, enabled, order, schemaVersion, json)
```

完整 `Rule` 序列化在 `json` 一列里（`schemaVersion` 冗余出来便于迁移判定）：

```text
Rule(
  id, name, enabled, order,
  matchMode: MatchMode,             // 8 种，见 §2.2
  fields: Set<MatchField>,          // 文本类字段
  metaFields: Set<MetaFieldKind>,   // 元信息字段
  extrasFields: Set<String>,        // extras 任意键
  keywords: List<String>,           // A 组
  excludeKeywords: List<String>,    // B 组（仅 TEXT_A_NOT_B）
  regex: RegexConfig?,              // 仅 REGEX 模式
  keywordGroups: KeywordGroupsConfig?,  // V12.2，仅 TEXT_GROUPS（可空 → 旧 JSON 零迁移）
  scope: RuleScope(type, packages),
  actions: RuleActionConfig,
  deviceState: DeviceStateCondition
)

RuleActionConfig(
  block: Boolean, silentRemove: Boolean,
  snooze: SnoozeConfig?, replace: ReplaceConfig?,
  readAloud: Boolean,
  danmaku: DanmakuStyle?, float: FloatStyle?,
  floatTrigger: OverlayTriggerConfig?,
  aggregation: AggregationConfig?
)
```

**演进规则（必须遵守）**：新增字段一律**带默认值的可空/可选键**，老 JSON 缺键即取默认，
新分支不进入；结构性变更走 `RuleJsonMigrator` 迁移链（V1→V2 → snooze → 清 focus → 渐变重构），
`needsWriteback()` 判定是否需回写。**Room version 不因规则字段变化而升。**

### 3.2 其它表

| 表 | 关键列 | 说明 |
| --- | --- | --- |
| `notification_records` | recordId, key, notifId, packageName, appName, postTime, result, executedActionsJson, hitFieldsJson, extrasJson, restoredAt, ruleId, ruleName | 流水，滚动约 1000 条 |
| `stats_daily` | packageName, appName, epochDay, filtered, passed | 按天聚合，主键 (packageName, epochDay) |
| `pending_reposts` | id, ruleId, triggerAt, originalKey, packageName, appName, repostTitle, repostText, replaceConfigJson, channelUseAppName… | 推迟×替换的到点重发任务 |
| `aggregation_items` | id, ruleId, listIndex, value, createdAt | `{itemsN}` 的跨通知累积 |
| `blacklist` | packageName, appName | 无条件消除 |

> Room `version = 2`（V7 加了 `aggregation_items` + `pending_reposts` 两列，`MIGRATION_1_2` 纯增量，
> 迁移前复制 db 快照）。此后未再升版本。

### 3.3 备份封套

```json
{
  "app": "notification-filter",
  "kind": "backup",
  "version": 1,
  "exportedAt": 1735689600000,
  "rules": [ { "…规则完整 JSON…" } ],
  "blacklist": [ "com.tencent.mm" ],
  "settings": { "masterEnabled": true, "theme": "INDIGO", "darkMode": "SYSTEM",
                "showOngoing": false, "hideFromRecents": true }
}
```

- `app` / `kind` / `version` 任一不符 → 整体拒绝并给中文原因；
- `blacklist` / `settings` 缺失 → 按空处理（早期只有规则的备份仍可导入）；
- 单条规则坏掉 → 跳过并计入 `skippedRuleCount`，不拖垮整体；
- **规则解析必须复用 `RuleTransfer.import`**（只有一份实现）。

## 5. 关键设计决策（含红线，改之前务必先读）

1. **🔴 WebDAV 不能用 `HttpURLConnection`。**
   Android 与桌面 JDK 的 `HttpURLConnection` 只放行 7 个标准方法
   （GET/POST/HEAD/OPTIONS/PUT/DELETE/TRACE），WebDAV 的 `PROPFIND` / `MKCOL` 会直接抛
   `ProtocolException: Expected one of [...] but was PROPFIND`。
   解法：`core/backup/RawHttp.kt` 用 `Socket`/`SSLSocket` 手写 HTTP/1.1
   （任意方法、任意头、显式 Content-Length、chunked 响应解析、跳过 1xx、跟随 301/302/303/307/308）。
   **不要改回 HttpURLConnection，也不要用反射改私有 method 字段。**

2. **🔴 正则必须在热路径上缓存。** 规则匹配（`RuleEngine`）与内容提取（`ItemExtractor`）
   各有 LRU 编译缓存。正则编译成本远高于匹配本身，音乐/下载类通知每秒刷新时尤其明显。

3. **🔴 流水就地合并靠 `onRemoved` 区分。** 不要试图用「内容指纹 / 节流」解决刷屏：
   指纹只挡「内容完全没变」，进度类通知永远算变；节流只降频不降行数。

4. **🔴 覆盖层动画 `NONE` = 真·零动画**（`snapTo(1f)` + 直接摘窗口），不能倒放入场进度。

5. **🔴 递归/循环类告警**：`remember { 耗时调用() }` **不是异步**，仍在主线程同步执行。
   要异步用 `produceState + withContext(IO)` 或 ViewModel 里的可取消 Job。

6. **澎湃 OS 焦点通知 / 超级岛不可实现**：需要小米公司主体授权（企业开发者邮件申请），
   个人侧载拿不到。V5 已整体删除相关代码与规则字段（迁移时清除并写回）。

7. **歌词功能已整体删除**（V9.8/V10）。AVRCP 无歌词字段；无障碍抓屏触碰隐私红线且拿不到
   自定义 View 文本；读他人私有 `.lrc` 被 scoped storage 封死。**媒体字段（`media.*`）保留**，
   那套能力与歌词无关，不要一起删。

8. **「静音消除」只能做到渠道级**：`onNotificationPosted` 回调时声音已发出，
   公开 API 无法只静音单条。

9. **不要给 `notification_records.key` 加索引**：`ORDER BY recordId DESC LIMIT n` 走 rowid
   反向扫描，命中即停，代价远小于一次迁移。

## 8. 质量要求

- **单测 426 例全绿**，覆盖：规则 JSON 迁移与兼容、7 种匹配模式、占位符渲染、
  正则提取与捕获格式、推迟时刻计算、备份封套编解码、备份命名与保留策略、
  自动备份触发时刻、原始 HTTP 客户端（进程内假服务器逐字节校验请求 + chunked 响应）、
  WebDAV 目标全流程（进程内迷你 WebDAV 服务器）。
- **纯逻辑层必须无 Android 依赖**，否则上述单测跑不起来。
- 已知局限：单测**不覆盖**「参数 → 实际像素位置 / 尺寸」，也不覆盖「调用链能否走到副作用」。
  UI 参数与覆盖层行为**只能真机验收**。新增功能必须提供一条「能走到副作用」的证据
  （例如进程内假服务器 + 真实客户端联调），不能只靠编译通过。
- 关键路径必须记日志（`NfLog`，tag = `NF:类名`），但**绝不打印通知正文/标题/extras 内容**。

## 9. 已知限制（设计取舍，不是 bug）

1. 覆盖层依赖悬浮窗权限；未授权时动作记 `OVERLAY_SKIPPED`（红色标签），不会静默丢弃。
2. 进程被系统回收后覆盖层窗口消失，不做常驻守护。
3. 焦点通知 / 超级岛不支持（见 §5 第 6 条）。
4. 「静音消除」作用于整个通知渠道（平台限制，见 §5 第 8 条）。
5. 自动备份由系统调度，可能延迟几分钟；小米机型需允许自启动。
6. 流水约 1000 条滚动淘汰，不做无限历史。
7. 备份不含流水与统计（体量大且换机后意义有限）。
